## Общий вердикт

Спека написана профессионально. Архитектурный скелет — правильный. Но есть несколько технических проблем разной степени серьёзности, которые нужно решить до начала разработки.

---

## ✅ С чем полностью согласен

**Гибридная архитектура (cloud + local)** — единственно разумное решение для данного железа. Попытка гнать 200 страниц через локальный VLM на CPU — это 2–4 часа ожидания. Облако здесь не роскошь, а необходимость.

**SiliconFlow как основной провайдер** — выбор оправдан. Для РФ это реально работающий вариант с OpenAI-совместимым API, бесплатными моделями и CosyVoice2 для TTS. Альтернативы (DashScope, OpenRouter) либо блокируются, либо требуют крипто-оплаты.

**Паттерн абстракции Provider (ABC-классы)** — отличное архитектурное решение. Позволяет менять провайдера одной строкой в конфиге, писать моки для тестов, добавлять новые API без переписывания пайплайна. Это профессиональный подход.

**JSON-схема как промежуточный формат** — правильно. Каждый этап пишет структурированный JSON, следующий этап читает его. Легко отлаживать, легко переиграть один этап без перезапуска всего пайплайна.

**CosyVoice2-0.5B для TTS** — хороший выбор. 0.5B, поддержка эмоций, русский язык, есть ONNX-экспорт от сообщества.

## ⚠️ Серьёзные проблемы

### 1. Критический пропуск: нет этапа визуального описания панелей

Это самая большая дыра в спеке.

В Stage 2 есть поле `"caption"` в JSON после OCR:
```json
"caption": "Two characters discuss their escape plan in a tense moment"
```

Но нигде не объяснено **откуда берётся этот caption**. DeepSeek-OCR извлекает текст, а не описывает что нарисовано. Если отдать на анализ сюжета только OCR-текст из баблов — получим текстовый анализ диалогов, а не понимание комикса.

Комиксы — визуальный медиум. Немые панели, мимика персонажей, экшен-сцены, смена локации — всё это несёт сюжетную информацию, которой в тексте баблов нет вообще.

**Что нужно добавить:** отдельный Stage 2b — описание визуального содержимого каждой панели через VLM. И для этого есть реально лёгкий вариант:

**Florence-2-large** (~800 MB, Microsoft) — ONNX-экспортируемый, работает на CPU за 5–15 секунд на панель. Задача `DETAILED_CAPTION` даёт пригодные описания. Это именно то что нужно: "Two men in armor stand in a dark corridor, one pointing urgently toward an exit."

Без этого Stage 4 (Story Understanding) работает вслепую.

---

### 2. OCR баблов без детектора баблов

В спеке предполагается что OCR-модель сама найдёт бабл в панели и вернёт его bbox. DeepSeek-OCR — это модель для документов, она не специализирована под comic bubbles и не гарантирует правильную атрибуцию "кто что говорит".

Между тем у тебя уже есть готовый инструмент: **manga YOLO-детектор (class 1 = text_bubble)**. Это правильная последовательность:

```
Panel PNG
  → yolo_manga INT8 → bbox баблов
  → crop каждого бабла
  → EasyOCR / PaddleOCR (классический, не VL) → текст
```

EasyOCR + PaddleOCR classic работают локально, ~0.5 сек на бабл, не требуют API-ключа. Качество на печатном тексте — отличное.

---

### 3. Story Understanding работает только с текстом

Код в Stage 4 отправляет LLM только `panels_data` (OCR-текст) — без изображений, без visual captions. При этом модели Qwen3.5-122B-A10B и 397B указаны как "с поддержкой Vision" — но Vision через SiliconFlow API требует передачи base64 картинок в `content`, чего в примерах нет.

Если не передавать визуальное содержимое — смысл Vision-моделей теряется, можно взять обычный Instruct и сэкономить.

**Правильный подход:** передавать Florence-2 captions как текст в промпт. Это дешевле токенов чем картинки, работает с любой LLM, и даёт модели полноценный контекст.

---

### 4. Timing в видеосборке — недооценённая сложность

Stage 7 написан очень схематично. Синхронизация аудио и видео — нетривиальная задача:

- Длина аудио TTS непредсказуема (зависит от длины текста)
- Панель должна быть на экране пока звучит реплика персонажа на ней
- Нарратор и персонажи не должны перекрываться
- Переход между панелями должен коррелировать со сменой реплики

Это требует **явного расчёта тайминга** по аудио-длинам, а не статического `duration_seconds` в JSON-сценарии.

## 🟡 Замечания средней важности

**Hunyuan-MT-7B через Ollama** — `ollama pull hunyuan-mt:7b` скорее всего не сработает. Официального Ollama-образа для Hunyuan-MT нет, только HuggingFace weights + специфичная архитектура. Нужно уточнить реальный способ локального запуска.

**Rate limits на "бесплатных" моделях SiliconFlow** — спека обещает $0 за 500 панелей через DeepSeek-OCR FREE. Реальность: у бесплатных моделей есть rate limits (обычно 5–20 RPM). При 500 панелях и 20 RPM — это 25+ минут только на ожидание между запросами. Это нужно учесть в batch-логике с retry + delay.

**PaddleOCR-VL-1.5 локальный ONNX** — код `ort.InferenceSession("models/paddleocr_vl_1.5.onnx")` написан как заглушка. Реальный экспорт PaddleOCR-VL в ONNX нетривиален (PaddlePaddle → ONNX конвертация имеет известные проблемы с VLM-архитектурами).

## 💡 Моё мнение по архитектуре

Предлагаю скорректированный пайплайн:

```
Stage 1: Split (YOLO → PNG панели) ✅ уже есть

Stage 2a: Bubble detection + OCR
  └─ yolo_manga INT8 (class 1) → bbox баблов
  └─ EasyOCR/PaddleOCR classic (локально, бесплатно) → текст

Stage 2b: Visual description (НОВЫЙ, критичный)
  └─ Florence-2-large ONNX (800MB, CPU, ~10s/панель) → caption
  └─ или VLM API (Qwen2-VL через SiliconFlow) если нужно лучше

Stage 3: Translation (опционально)
  └─ Hunyuan-MT-7B via SiliconFlow FREE

Stage 4: Story Understanding
  └─ Qwen2.5-7B-Instruct FREE (ECONOMY) — вход: OCR + captions
  └─ Qwen3.5-122B-A10B (QUALITY) — то же + при необходимости картинки

Stage 5: Script generation
  └─ та же модель, follow-up prompt → JSON сценарий с тайминг-расчётом

Stage 6: TTS
  └─ CosyVoice2-0.5B локально
  └─ или SiliconFlow CosyVoice2 API

Stage 7: A/V assembly
  └─ timing-aware ffmpeg-сборка (длина аудио → duration панели)
```

**Ключевое изменение:** Stage 2b (Florence-2) закрывает самую большую дыру в спеке — отсутствие визуального понимания.
